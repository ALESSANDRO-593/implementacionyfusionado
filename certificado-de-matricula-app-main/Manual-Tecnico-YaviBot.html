01 INTRODUCCIÓN

Descripción general del sistema

YaviBot es un asistente conversacional para estudiantes y docentes del Instituto Yavirac, construido como aplicación móvil híbrida (Ionic/Angular) con un backend de automatización (n8n) que actúa como API completa sobre una base de datos PostgreSQL institucional.

El sistema resuelve, de principio a fin y sin intervención de un panel administrativo dedicado, los trámites de emisión de Certificado de Matrícula con verificación pública por código QR, Anulación de Matrícula, y Reporte de Incidencias de Laboratorio (para el rol docente). El Reseteo de Contraseña del correo institucional está implementado a nivel de backend pero, en la versión actualmente publicada, no se expone como opción del menú — ver sección 7.

La identidad del usuario se resuelve con un único flujo, sin pantalla de login: cédula de identidad seguida de un código de verificación de un solo uso (OTP) enviado al correo institucional. El mismo flujo distingue automáticamente si quien lo usa es un estudiante o un docente, y adapta el menú de opciones que ve.

Principio rector del proyecto

n8n no consume una API: n8n es la API. No existe un servidor Node/Express/NestJS intermedio. Cada trámite es un workflow de n8n con un nodo Webhook como punto de entrada; toda la lógica de negocio —validaciones, generación de códigos únicos, reglas de idempotencia— vive dentro de esos workflows.

Alcance dentro del proyecto de titulación

Este manual documenta la aplicación móvil del proyecto de titulación "Desarrollo de una aplicación web y móvil para automatizar los procesos de mesa de ayuda mediante la herramienta de orquestación n8n en el Instituto Superior Tecnológico Yavirac". El objetivo general del proyecto es optimizar los procesos administrativos del instituto reduciendo los tiempos de atención y seguimiento de requerimientos; esta app cubre específicamente los trámites de Estudiante y el rol Docente descritos en la sección Trámites del sistema. La gestión administrativa (paneles de Secretaría/TI, seguimiento de tickets, asignación manual) corresponde a la aplicación web del proyecto, construida de forma independiente por otro equipo — desde agosto de 2026 ambas aplicaciones operan integradas sobre el mismo servidor y la misma base de datos institucional real, ver sección 11, Despliegue en producción.

02 ARQUITECTURA

Arquitectura general

Tres capas, con una responsabilidad clara y sin lógica de negocio filtrándose entre ellas.

App Ionic (certi-matricula-app · presentación) │ HTTPS / JSON ▼ n8n (API + lógica de negocio) │ SQL ▼ PostgreSQL (esquema compartido con la web)

Capa 1 — Presentación

La app Ionic/Angular (certi-matricula-app/) no contiene reglas de negocio: solo llama webhooks y renderiza lo que reciben. La identidad del usuario, el menú disponible y el estado de la conversación viven en un único componente de chat conversacional (chat.page.ts) que orquesta cada trámite como una máquina de estados.

Capa 2 — API y lógica de negocio

Cada archivo en n8n-backend/workflows/ es, a la vez, la definición de un endpoint HTTP y la implementación completa de su lógica: validaciones, verificación de sesión OTP, generación de códigos únicos, envío de correos, idempotencia. No existe una capa de código separada — los nodos Webhook, Postgres, IF y Code de cada workflow son, literalmente, el backend.

Capa 3 — Datos

PostgreSQL 16. El esquema es real y compartido con el sistema web/panel administrativo del instituto (~25 tablas en total); esta app únicamente lee y escribe el subconjunto que necesita (ver Modelo de datos). Si el esquema cambia, solo se ajustan los nodos Postgres de los workflows afectados — el contrato hacia la app no cambia.

Por qué importa esta separación

Permite que dos equipos (esta app y el sistema web) construyan de forma independiente sobre la misma base de datos, sin coordinar despliegues, mientras respeten las mismas restricciones de integridad (claves únicas, estados válidos) definidas a nivel de esquema. Esto dejó de ser un principio de diseño y pasó a ser un hecho verificado: en agosto de 2026 los workflows de esta app se desplegaron junto a los del equipo web, en la misma instancia de n8n y la misma base de datos, sin modificar el trabajo del otro equipo — ver sección 11.

Nombres reales confirmados en producción

El diseño original de esta app previó una tabla asignaciones_responsables para resolver a quién notificar cada trámite nuevo. Al integrar con la base de datos real del instituto (agosto 2026) se confirmó que esa resolución vive en rol_tipos_solicitud — mismo propósito, distinto nombre. Los workflows se ajustaron a la tabla real; el modelo lógico no cambió.

Decisiones de modelado relevantes

  • El código único del certificado (codigoUnico) es un identificador propio de qr_codigos, con restricción UNIQUE a nivel de base de datos — un QR duplicado es estructuralmente imposible, sin importar qué cliente escriba.
  • Idempotencia forzada en dos niveles: el workflow verifica antes de insertar (para responder con datos existentes en vez de un error), y además certificados tiene UNIQUE(estudiante_id, periodo_lectivo_codigo) — cierra la condición de carrera si dos solicitudes llegan casi al mismo tiempo.
  • Reemisión de certificado sin duplicar QR: si el estudiante vuelve a pedir su certificado del mismo periodo, se actualiza fecha/hora sobre la misma fila (mismo qr_id de siempre) — el QR impreso nunca cambia, pero la fecha mostrada, tanto en el PDF como al escanearlo, siempre refleja la última emisión.
  • codigo en tickets y alertas es NOT NULL y UNIQUE en el esquema real: se inserta con un valor temporal aleatorio y se reemplaza por el código correlativo definitivo (TK-000029, AL-000021) inmediatamente después del insert, dentro del mismo workflow.
  • Estados de tickets y alertas en español (Pendiente / En Proceso / Resuelto) — mismo vocabulario que usa el panel administrativo del equipo web, sin traducción intermedia.
05 CONTRATO

Especificación de la API

11 workflows con Webhook, autenticados con cabecera X-Api-Key. Formato de respuesta plano (sin envelope): éxito → 200 con el objeto/arreglo directo; error de negocio → 4xx con { "error": "mensaje" }.

Dos capas de autenticación

La X-Api-Key filtra tráfico que no pasa por la app, pero es la misma para todos los usuarios. La protección real contra "conozco la cédula de alguien y quiero actuar en su nombre" es la sesión OTP: los endpoints que modifican datos o exponen información personal exigen, del lado del servidor, un otp_codigos.usado = true de los últimos 20 minutos para esa cédula.

5.1 — Identidad y verificación

POST/consultar-estudiante reCAPTCHA v2

Busca la cédula en estudiantes; si no hay match, busca en docentes. Responde siempre 200 — null si no existe, o el objeto con tipoUsuario: "ESTUDIANTE" | "DOCENTE". Único paso sin OTP previo, protegido en su lugar con reCAPTCHA v2 contra enumeración de cédulas.

Request
{ "cedula": "0102030405" }
Response 200
{ "tipoUsuario": "ESTUDIANTE",
  "nombres": "…", "carrera": "…" }
POST/enviar-ticket-verificacion

Genera un código de 6 dígitos, lo guarda con expiración de 10 minutos y lo envía al correo institucional del usuario identificado. Cooldown de 60s por cédula. Responde correoEnmascarado (ej. an**@yavirac.edu.ec), nunca el código.

POST/verificar-ticket

Compara el código recibido contra otp_codigos. La app solo muestra el menú cuando responde { "valido": true }. Límite de 5 intentos fallidos en 10 minutos por cédula — bloquea con 429 al superarlo.

5.2 — Certificado de matrícula

POST/generar-certificado-matricula Sesión OTPAutomático

Único trámite 100% automático del menú. Crea el código único y el registro del certificado; si ya existía uno para ese estudiante y periodo, actualiza su fecha en vez de duplicar el QR. Si el estudiante no tiene periodo_ingreso_id registrado en la base real (caso frecuente en los datos institucionales importados), el certificado se emite igual, omitiendo esa línea en vez de mostrar un dato inválido.

400 Cédula no matriculada en el periodo actual.
403 Sin sesión OTP válida reciente.
POST/enviar-certificado-pdfSesión OTP

La app genera el PDF real (membrete oficial + QR) en el navegador con certificado-pdf.service.ts, lo convierte a base64 y lo envía aquí para que n8n lo adjunte y lo mande por correo institucional.

POST/verificar-certificadoPúblico — sin login

El QR impreso codifica una URL pública que cualquiera puede escanear para validar autenticidad — funciona como firma digital de Secretaría. La cédula viaja siempre enmascarada (175****314). Código inexistente → 404 con autentico: false, nunca un 500.

5.3 — Trámites de estudiante

POST/crear-ticket-solicitudSesión OTP

Registra Anulación de Matrícula (o Consulta de estado) como ticket manual, resuelto por personal administrativo desde el panel del equipo web. Asigna responsable automáticamente vía rol_tipos_solicitud y le envía un aviso por correo. Idempotente: si ya existe un ticket activo del mismo tipo, devuelve el existente en vez de duplicarlo.

POST/consultar-ticketsSesión OTP

Lista los tickets del estudiante identificado, en el mismo estado (Pendiente / En Proceso / Resuelto) que ve el personal administrativo en su panel — misma tabla, sin sincronización aparte.

POST/resetear-contrasena-correoSesión OTPAutomáticoNo expuesto en el menú actual

Genera una contraseña temporal y la aplica de inmediato. Implementado y probado a nivel de workflow; se retiró del menú visible de la app — ver sección 7 para el detalle.

5.4 — Rol docente

POST/consultar-laboratorios

Catálogo de laboratorios, usado para poblar el paso de selección al reportar una incidencia.

POST/reportar-incidencia-laboratorioSesión OTP

El backend vuelve a validar del lado del servidor que la cédula sea de un docente real, y además resuelve su cuenta en usuarios_panel por cédula — el reporte queda registrado como si lo hubiera creado un usuario real del panel administrativo. Foto adjunta opcional (JPEG/PNG, máx. 5MB), guardada en disco, nunca como binario en la base de datos. Genera un código correlativo real (AL-000021) y notifica por correo al Responsable de Laboratorios asignado.

06 SEGURIDAD

Medidas de seguridad implementadas

Cada control responde a una amenaza concreta identificada durante el desarrollo, no a una lista genérica de buenas prácticas.

  • Autenticación de webhook (X-Api-Key) — filtra tráfico que no pasa por la app antes de ejecutar cualquier lógica.
  • reCAPTCHA v2 en /consultar-estudiante, el único paso sin OTP previo — contra enumeración de cédulas.
  • Sesión OTP verificada server-side (no solo en la app) en los endpoints que actúan en nombre de un estudiante/docente específico — ventana de 20 minutos.
  • Cooldown y límite de intentos al reenviar y verificar el código — contra fuerza bruta y abuso de envío.
  • Idempotencia forzada a nivel de base de datos (restricciones UNIQUE) además del chequeo del workflow — cierra condiciones de carrera entre esta app y el sistema web.
  • Enmascarado de datos sensibles — correo y cédula en las respuestas donde no hace falta el dato completo.
  • Contraseña nueva solo por correo — nunca en la respuesta HTTP ni en el log de auditoría del reseteo.
  • Validación server-side redundante — ej. reportar-incidencia-laboratorio reconfirma que la cédula sea de un docente real, sin confiar en la app.
  • Auditoría de eventos (tabla eventos) para trámites creados, asignados y reseteos ejecutados.
Nota de operación — API key compartida en el repositorio

La X-Api-Key del servidor institucional está versionada en environment.ts/environment.prod.ts a propósito, para que el equipo que continúa el desarrollo (ver sección 11) pueda clonar el repositorio y ejecutar la app sin pasos adicionales. No sustituye a la sesión OTP como control de acceso a datos personales — ver "Dos capas de autenticación" en la sección anterior.

Reseteo de contraseña: implementado, pero fuera del menú

El trámite se construyó como requerimiento inicial de la coordinación académica: el estudiante, ya autenticado por cédula + OTP, resetea su contraseña al instante, sin intervención humana, reutilizando la prueba de otp_codigos.usado en vez de crear un mecanismo de sesión nuevo. El workflow (/resetear-contrasena-correo) sigue activo y probado en el servidor. La opción se retiró del menú de la app en la fase de cierre del proyecto; el código de la app y del workflow permanece en el repositorio para reactivarla con un solo cambio si se decide reincorporarla.

Consultar estado de tickets: reincorporado

Esta opción existió, se retiró temporalmente durante el desarrollo, y se reincorporó al integrar con el servidor compartido — el estudiante puede ver en la app el mismo estado (Pendiente / En Proceso / Resuelto) que el personal administrativo actualiza desde su panel, sobre la misma tabla tickets.

08 IDENTIDAD

Identidad dual: estudiante / docente

Segunda identidad de usuario agregada sin tocar el flujo de identificación existente ni crear una pantalla de login separada.

  1. POST /consultar-estudiante busca primero en estudiantes; si no hay match, busca en docentes. La respuesta incluye el discriminador tipoUsuario.
  2. POST /enviar-ticket-verificacion hace la misma búsqueda dual para saber a qué correo enviar el OTP.
  3. POST /verificar-ticket no distingue rol — valida el OTP contra otp_codigos por cédula únicamente.
  4. La app guarda el Usuario identificado (unión discriminada Estudiante | Docente) y elige el menú según tipoUsuario: el estudiante ve sus trámites; el docente ve únicamente Reportar incidencia en laboratorio.
Foto de incidencia

Se envía como base64 desde <input type="file" capture="environment"> (sin plugin nativo de cámara), el workflow la escribe en disco dentro del volumen de almacenamiento compartido y solo entonces registra la fila en adjuntos. Adjuntar foto es siempre opcional; si falla el guardado en disco, el reporte se guarda igual, sin foto.

10 ENTORNO LOCAL

Instalación y ejecución local

Para desarrollar o probar cambios sin afectar el servidor compartido en producción — ver sección 11 para correr contra el servidor real.

Backend (n8n + PostgreSQL)

  1. Levantar los contenedores: docker compose up -d desde n8n-backend/.
  2. Abrir n8n (http://localhost:5678) e importar los 11 workflows.
  3. En cada nodo Postgres, configurar la credencial real de base de datos.
  4. En cada nodo Webhook, configurar la credencial Header Auth (X-Api-Key).
  5. En los nodos de envío de correo, configurar la credencial SMTP.
  6. Poner la Secret Key de reCAPTCHA v2 en el nodo "Verificar CAPTCHA (Google)".
  7. Activar los 11 workflows.

Frontend (Ionic/Angular)

  1. npm install dentro de certi-matricula-app/.
  2. Confirmar en environment.ts: usarMock: false y n8nBaseUrl: 'http://localhost:5678/webhook'.
  3. npx ng serve — la app queda disponible en http://localhost:4200.

Nota — la app también puede correr con environment.usarMock = true, sin backend real, contra datos simulados que respetan el mismo contrato — útil para desarrollar la interfaz sin depender de n8n.

11 DESPLIEGUE

Despliegue en producción

En agosto de 2026, esta app dejó de ser un proyecto local y pasó a operar sobre la infraestructura real del instituto, compartida con la aplicación web construida por otro equipo del mismo proyecto de titulación.

Arquitectura del servidor compartido

Un único VPS institucional aloja, en contenedores Docker separados, el n8n compartido, la base de datos PostgreSQL real (estudiantes, docentes, tickets, certificados y alertas del instituto) y nginx como punto de entrada. nginx enruta por prefijo:

RutaSirve
/Panel administrativo del equipo web
/app/Esta aplicación (build de producción de Ionic/Angular)
/webhook/n8n — todos los workflows, de ambos equipos

Los 11 workflows de esta app conviven en la misma instancia de n8n que los del equipo web (identidad, panel, alertas), identificables por el prefijo App Matrícula - en su nombre. Usan rutas de webhook sin prefijo (generar-certificado-matricula, crear-ticket-solicitud, etc.), que no colisionan con las del equipo web (chatbot/, panel/, admin/).

Adaptaciones al esquema real

Integrar contra la base de datos real (1401 estudiantes, 107 docentes) expuso diferencias puntuales frente al esquema de desarrollo local, todas corregidas a nivel de workflow sin tocar el contrato de la app:

  • asignaciones_responsables no existe en producción; la resolución de responsable vive en rol_tipos_solicitud.
  • tickets.codigo y alertas.codigo son NOT NULL y UNIQUE en producción — se corrigió el insert para generar un valor temporal aleatorio (no un literal fijo, que habría chocado con la restricción única desde el segundo registro) antes de asignar el código correlativo definitivo.
  • alertas.profesor_id referencia usuarios_panel.id, no docentes.id — el workflow de incidencias resuelve ambas tablas por cédula antes de insertar.
  • El certificado de matrícula omite la línea de "periodo de ingreso" cuando el dato no está registrado para ese estudiante en la base real, en vez de mostrar texto inválido.

Empaquetado como APK (Android)

La app se compila como APK nativo con Capacitor, usando Android Studio + su JDK embebido y el SDK de Android (API 36). Dos ajustes de configuración fueron necesarios específicamente para que la app nativa pudiera hablarle al backend, que corre sobre HTTP plano (el VPS aún no tiene un dominio propio ni certificado TLS):

Bloqueo de contenido mixto en el WebView

Por defecto, Capacitor sirve la app bajo el origen interno https://localhost. Cualquier llamada desde ahí a un endpoint http:// se bloquea como "contenido mixto" por el motor del WebView — no por Android como sistema operativo, así que ajustar solo usesCleartextTraffic/networkSecurityConfig no alcanza. Solución aplicada en capacitor.config.ts: server.androidScheme = 'http', sin cambiar el hostname. Bajar el esquema local a http iguala el protocolo con el del backend sin generar colisión de rutas (ver nota siguiente).

Por qué no usar el mismo hostname que la API

Un primer intento configuró server.hostname igual a la IP del backend, para que la app "compartiera origen" con la API. Efecto real: Capacitor empezó a interceptar toda llamada a esa IP y a responder con los archivos locales de la propia app (devolvía su index.html donde se esperaba JSON). Diagnosticado con un mensaje de depuración temporal en el manejador de errores del chat, que expuso el cuerpo de la respuesta real. Revertido: el hostname se deja en su valor por defecto.

Respaldo y continuidad

Antes de compartir acceso al servidor con equipos adicionales, se generó un respaldo completo y verificado: volcado SQL de la base de datos completa, copia del volumen de datos de n8n (workflows y credenciales), y copia de los directorios web de ambas aplicaciones — almacenado tanto en el propio VPS como fuera de él, como punto de restauración si un cambio posterior de otro equipo afecta el sistema.
